What is this tool for?

AI System Architecture Designer is a visual whiteboard for planning production AI systems — RAG chatbots, agents, LLM APIs and ingestion pipelines. Instead of a static drawing, every box carries capacity, latency, replica and cost numbers, so the diagram can tell you where the system will break before you build it.

1

Assemble components

Combine an LLM, vector database, retriever, reranker, embedding model, API gateway, cache, queue, GPU server, guardrails and monitoring into one picture.

2

See the data flow

Connections show what calls what, how many requests per second travel along each link, and whether the call is synchronous, async or telemetry.

3

Find bottlenecks

Traffic is propagated through the graph. Components above 75% utilisation turn amber, above 100% turn red, and the tool tells you how many replicas would fix it.

4

Understand dependencies

Select a component to highlight everything upstream and downstream of it, and see its “blast radius” — what breaks if it goes down.

5

Estimate latency & cost

The slowest (critical) path gives an end-to-end latency estimate; replicas × unit cost gives a monthly infrastructure estimate.

6

Export & share

Export as Mermaid (for GitHub, Notion, Confluence, docs-as-code) or as a standalone SVG image. Save/open designs as JSON.

Who it's for: ML / platform engineers sizing an inference stack, backend developers designing a RAG feature, architects preparing a design review, and teams documenting what they already run.

How to use this tool

  1. Start from a template or a blank canvas. Use the Templates… menu (e.g. RAG chatbot) to get a working example, or Blank canvas to start fresh.
  2. Add components. Drag an item from the Components list on the left onto the canvas, or simply click it. Use the search box to filter.
  3. Connect them. Drag from the small circle on the right edge of a component onto another component. The arrow means “calls / sends data to”. Alternatively select a component, then Shift+click the target.
  4. Describe each piece. Click a component to edit it in the right-hand Inspector: name, capacity per replica (requests/second), latency (ms), number of replicas, monthly cost per replica, and — for caches — the hit rate.
  5. Describe each connection. Click an arrow to set its label (e.g. “top-5 context”), its type (synchronous, async or telemetry) and calls per request (e.g. an agent that calls the LLM 3 times).
  6. Set the traffic. Enter the expected requests per second in the toolbar's Traffic box. Watch the utilisation bars, red/amber components and the Analysis panel update live.
  7. Fix the bottlenecks. Read the Findings list: add replicas, put a cache in front of the LLM, move work to an async queue, or add monitoring until the design is green.
  8. Export. Click Export Mermaid to copy or download Mermaid code, or Export SVG to download an image. Use Save to keep an editable JSON copy (your work is also auto-saved in this browser).

How the analysis works

Traffic propagation

  • Traffic enters at Client / Users nodes (or, if there are none, at components with no incoming connections) and is split evenly between them.
  • Every component forwards the traffic it receives to each component it calls, multiplied by the connection's calls per request.
  • A Cache forwards only its misses: load × (1 − hit rate).
  • A Load Balancer splits its traffic evenly across its targets.
  • Telemetry links send events to monitoring but never carry user traffic further.

Bottlenecks

  • utilisation = load ÷ (capacity per replica × replicas)
  • ≥ 75% → amber (near capacity), > 100% → red (overloaded; requests will queue or fail).
  • The component with the highest utilisation is the primary bottleneck; max sustainable traffic = traffic ÷ highest utilisation.
  • Single points of failure (1 replica on the request path), cycles, missing monitoring, missing caches and disconnected parts are also reported.

Latency

  • Only synchronous calls add to user-facing latency; async work runs off the request path.
  • A chain of calls adds up; parallel branches take the slowest one. The slowest chain is the critical path (purple).
  • With a cache on the path, an average is also shown: hit × latency-to-cache + miss × full latency.

Limits of the model

  • This is a back-of-the-envelope planning model, not a load test. Use measured numbers from your own benchmarks where you can.
  • Latency shown is unloaded latency; real latency rises sharply as utilisation approaches 100%.
  • For LLMs, capacity depends heavily on prompt/output length, batching and hardware — treat the defaults as placeholders.
